How much longer? Text expansion across the 24 EU languages

Translated text is usually longer than its English source — by a different amount in every language. This note measures that expansion empirically, explains why it happens, checks it against the published literature, and works out what it means for keeping translated PDFs readable without the patchwork of shrunken fonts.

Corpus: 16 domain sentences (agricultural / technical) Engines: DeepL (22 langs) · LLM (mt, ga) Metric: character-length ratio (translated ÷ English) Run: scratchpad/expansion_results.json

What was measured

AMethod

16 English sentences drawn from the agricultural / technical register of real EU-FarmBook knowledge objects were translated into every other EU language, and the character-length ratio (translated ÷ English, including spaces) was recorded for each. Character count is the standard first-order proxy for how much horizontal space a string needs — the same measure the W3C and IBM localization guidance use.

Translations used DeepL for the 22 languages it supports — professional-grade output is the most faithful estimate of how long natural text really is. Maltese and Irish, which DeepL does not cover, went through the project LLM.

Two data-quality caveats. Irish is excluded: the LLM degenerated into repetition loops (mean 7.9×, one output 31× the source), so its numbers are meaningless — published Celtic estimates should be used instead. Maltese is length-plausible but of lower translation quality. And character count is a proxy: true rendered width depends on the font's per-glyph widths (relevant for Greek and Cyrillic), which the implementation phase should measure directly.

The linguistics

CWhy each family behaves as it does

Every translation carries a universal upward pull — the explicitation hypothesis (Blum-Kulka 1986): translators make implicit relations explicit, adding words. What each language nets out at is that pull minus its own morphological compactness.

Romance+22%
fr, es, it, pt, ro

Periphrastic (multi-word) constructions, obligatory articles and prepositions, longer average word length.

Greek+20%
el

Polysyllabic vocabulary and article-heavy syntax; expands like the Romance group despite a different script.

Germanic (continental)+18%
de, nl

Compounding cuts word count but not character count; longer words and separable structures win out. German also makes very long unbreakable tokens — a line-wrapping hazard.

Finnic / Uralic+9%
fi, et, hu

Agglutination packs many grammatical markers into one long word: far fewer words, only modestly more characters.

Baltic+6%
lt, lv

Inflected and article-free, but longer word forms keep expansion mild.

Slavic+5%
bg, pl, cs, sk, sl, hr

No articles to render and case endings replace prepositions — several contract below English. Bulgarian is the exception (+16%): it is the one Slavic language with a definite article.

Scandinavian+3%
da, sv

Compact, article-light Germanic languages that stay very close to English length.

Does it hold up?

DAgreement with published figures

The measured numbers land squarely on the established benchmarks, which is the main check that the dataset is sound. IBM's globalization guidance and the W3C both put French/Spanish at roughly +20–25% and German as high as +35%; the measurements here reproduce that ordering and magnitude.

IBM expansion table (via W3C), by source length: up to 10 chars → +200–300%; 11–20 → +180–200%; 21–30 → +160–180%; 31–50 → +140–160%; over 70 → ~+130%. The shorter the string, the larger the relative growth — which is why isolated headings and captions overflow worse than paragraphs.

The point of all this

EWhat it means for font sizing

Because expansion is systematic per language, a per-language baseline font size is well founded — far better than shrinking each block independently, which produces the uneven, patchy result users flagged. To fit L× more text in a fixed box:

single-line elements (headings, captions that must not wrap) → font ≈ 1 / L
reflowing paragraphs (most body text) → characters × fontsize² ≈ area → font ≈ 1 / √L

So the practical per-language baseline scale for body text (the "font scale" column above) runs from:

French · 0.88 (12% smaller)
German / Spanish · 0.90
Dutch / Hungarian · 0.94
Finnish / Baltic · 0.96–0.97
Slovenian / Czech / Croatian · 1.00–1.02 (full size)

Why not a single uniform shrink. Per-sentence expansion varies widely (French individual sentences ran 1.07 to 1.84 — the Range column). A lone factor captures the central tendency, not every block. The recommended design is a hybrid: set the document-wide starting size for the language from its baseline scale, harmonize size within groups of same-styled sibling blocks, and keep a small bounded local shrink for the residual outliers — consistent by default, still tight where a block genuinely needs it.

This sits directly behind Q8 of the Q&A companion ("translations are longer than the original — how does the text still fit the page?") and the per-block fit logic in translate_pdf_direct.py. The harmonization half of this proposal has since been built and measured — see section F.

From proposal to code

FWhat was built, and does it look good?

The harmonization half of section E is now implemented in the direct engine (_harmonize_plan_font_sizes in translate_pdf_direct.py). This section records what it does, how it was measured on the real evaluation documents, and what the rendered pages actually look like.

Each block still gets its own fitted size first. Harmonization then groups blocks by (column · role · original source size) across the whole document and pulls each group to one shared size — the group's smallest fitting size, but never below 0.85× its median, so a single dense block becomes the lone smaller exception rather than dragging the group down. Sizes only ever shrink, so a harmonized block still fits the box its larger size fit.

Scope — the mental model. Not one size for the whole document, and not per paragraph: one size per sibling group, document-wide. Because original size is part of the key, a heading is never pooled with body text — the source document's designed hierarchy (heading > sub-heading > body > caption) is preserved, and only the unwanted jitter within a role is removed.

Does the page look worse with sizes varying by section?

The opposite, on inspection of rendered before/after pages. Harmonization fixes the "some sections bigger than others" effect rather than causing it: in the un-harmonized page the motor-oil section's body text rendered visibly larger than the body text of other sections — same role, different size — and after harmonization all same-role body matched. The size differences that remain are the intended hierarchy (blue section headings stay larger than body), which reads as correct because original size is preserved in the grouping key.

Two honest caveats seen in the render. A genuinely oversized line was an untranslated source leftover (a block that failed to fit kept its source at original size) — a translation-fidelity issue, not a harmonization artifact, and present in both images. And the "dense outlier goes smaller" case is bounded by the median floor; on the inspected page it did not visibly appear.

Why the per-language factors are not wired into sizing

Tempting as it is to pre-scale the starting font by a language's expansion factor, that was evaluated and deliberately left out. The fit search already measures each translated string's true rendered fit in the real font, so a statistical prior can only do harm — it would shrink blocks that actually fit fine at full size. The factors in this study therefore live as a reference module (app/pipeline/language_metrics.py) and documentation, not as an input to the sizing decision.
