🌍 OmniLingua — Questions & Answers

A growing FAQ about how the omnilingua document-translation service works internally. Each main question includes supporting questions you can expand for more detail. Diagram companion: docs/flow-technical.html.

Q1What happens when a document arrives — what is the first thing that happens?

Short answer: the upload lands on the single public endpoint POST /translate/document (defined in app/api/routes/translate.py:139), behind HTTP basic auth that covers every route — including /docs and /openapi.json. Before the file is even read, the request is validated: is the extension supported (.pdf .txt .doc .docx .ppt .pptx), is target_lang one of the 24 official EU language codes, is the optional engine valid, and — if a source_lang was given — is it different from the target? Any failure is an explicit 400 with a human-readable reason.

Only then is the file spooled to a private temp directory (with a sanitized filename) and routed purely by extension: PDFs go to the direct PyMuPDF pipeline, .txt/.docx/.pptx to native translation, and legacy .doc/.ppt through a LibreOffice conversion first. The translated file is streamed back as a download, and a background task deletes the temp directory after the response. (app/services/document_translate_service.py:55–192)

Supporting questions

What routes exist besides /translate/document?

Three others. GET /health is the liveness check. POST /translate/pdf and POST /translate/pdf/advanced are deprecated, hidden routes (include_in_schema=False) kept for older clients and internal experiments — the advanced one exposes PDF-only options the public API deliberately does not: the HTML layout engine, JSON text-mapping mode, saving intermediate HTML, and experimental image-text translation. New integrations must use /translate/document only. (translate.py:92, 167)

How does authentication work?

HTTP basic auth (BASIC_AUTH_USERNAME/BASIC_AUTH_PASSWORD) is attached as a FastAPI dependency on the application itself, so every route inherits it — there is no unauthenticated surface at all. Even the Swagger UI and the OpenAPI schema are re-exposed through custom auth-guarded handlers. A small script injected into the Swagger page sets the file input's accept attribute so the browser's file picker offers only the supported document types. (app/main.py:37–88, app/core/auth.py)

What exactly does validation check, in order?
  1. A filename is present and its extension is in the supported set.
  2. target_lang is present, and both language fields normalize to a valid two-letter EU code — regional forms like pt-BR or de_DE collapse to their base code first. (app/core/languages.py:40–64)
  3. engine is llm, deepl, or adaptive (empty falls back to the TRANSLATION_ENGINE env default, which itself defaults to llm).
  4. If both languages were supplied, they must differ.
  5. If the engine is deepl and the target is Maltese (mt) or Irish (ga), the request fails fast with a pointer to llm/adaptive — DeepL does not offer those languages, so there is no point doing any work.

(document_translate_service.py:55–106, app/core/engines.py:29–53)

Why are JSON, CSV, and XLSX rejected instead of supported?

Deliberate policy, documented under "Structured Files Guidance" in the README: translating structured data in place is dangerous. JSON keys, dataset identifiers, enums, codes, and programmatic column headers must never be translated — doing so breaks parsing, joins, and downstream pipelines — while only the human-facing values may be. That requires a dedicated extract-and-rebuild design per format, not a generic text pass, so these formats are refused until such support exists. Don't "just add" them.

What happens to the uploaded file on disk?

It is written into a fresh tempfile.mkdtemp directory with a sanitized stem (non-alphanumeric characters replaced, capped at 120 chars — so a hostile filename can't escape the directory). The output is auto-named <stem>_<target_lang><ext>; legacy inputs keep the modernized extension (a .doc upload returns a .docx). After the FileResponse is sent, a FastAPI background task removes the whole temp tree — nothing is retained. (document_translate_service.py:31–52, 123–136)

Q2Why are some PDFs rejected before translation even starts?

Short answer: because translating mathematics garbles it. Before any model is called, ensure_pdf_translation_allowed scans every page's text lines for three signals: math symbols (= ∑ ∫ √ ≤ ≥ ≈ ∂ × …), trailing equation numbers like (3.1), and math function calls (sin( log( argmax_ exp( …). If the document looks formula-heavy overall, the request is refused with HTTP 400 and the message "PDF translation is not supported for formula-heavy or equation-heavy documents." (app/pipeline/pdf_content_policy.py:79–131)

The gate runs for both PDF layout engines — the direct pipeline calls it as its very first step, and the HTML-engine path calls it before conversion — so there is no route around it. (translate_pdf_direct.py:509, pdf_translate_service.py:149)

Supporting questions

What makes a single line "formula-like"?

A line qualifies when any of these hold: it carries an equation number plus symbols or digits; it contains a math function plus at least one symbol or digit; it has ≥ 3 math symbols outright; or its symbol+digit density is high (≥ 35% of characters) while carrying almost no real words. Ordinary prose with an occasional "=" doesn't trip it — the rules require either repetition or density. (pdf_content_policy.py:47–76)

When does the whole document get rejected?

Three independent triggers, any one suffices:

  1. Density: ≥ 12 formula lines and they make up ≥ 8% of all text lines.
  2. Spread: a document of ≥ 3 pages with ≥ 8 formula lines appearing on ≥ 25% of its pages.
  3. Dense page: ≥ 12 formula lines total with ≥ 8 concentrated on a single page.

(pdf_content_policy.py:102–110)

Why reject the whole document instead of skipping the equations?

Because the direct engine redacts and rewrites regions of the page. Inline math is interleaved with prose in the same lines and blocks; skipping it reliably would require formula detection at sub-line precision, and getting it slightly wrong means either translated equations (nonsense) or redacted-but-unreplaced text (data loss). For a formula-heavy paper the honest answer is "not supported" — a clean 400 the caller can act on — rather than a subtly corrupted output.

Q3A PDF has no paragraphs — how does the service reconstruct the document's structure?

Short answer: PyMuPDF hands over individual lines with their coordinates, font, size, colour, and writing direction. extract_native_blocks.py then rebuilds paragraphs by merging consecutive lines — but only when geometry and typography both agree they belong together — and tags every resulting block with a kind (title, paragraph, bullet, caption, table, reference, …) that later stages use to decide how the block may be translated and re-laid-out.

The same module detects two-column layouts and re-orders blocks into human reading order (full-width header → left column → right column → full-width middle → footer), infers whether a block was centered, and maps rotated (vertical) text to a rotation the writer can reproduce. Getting this right is what makes the output look like the original — everything downstream depends on these blocks.

Supporting questions

Why is line merging needed at all?

Translation changes text length, and length changes line breaks. If each source line were translated separately, every line would be a fixed-width prison: words could not reflow across lines, so each line's translation gets squeezed (or shrunk) independently — the "ransom note" effect. Merging a paragraph's lines into one block lets the translation reflow naturally inside the paragraph's rectangle. An earlier, stricter merge rule that split every body line on tightly-leaded posters is explicitly called out in a comment as the cause of exactly that failure. (extract_native_blocks.py:110–117)

What must be true for two lines to merge?

All of: same page, same raw PyMuPDF block, same font name, no rotation, font-size delta ≤ max(0.75 pt, 8%), left edges within ~1.5 em, horizontal overlap ≥ 35% of the narrower line, and a plausible vertical gap — including up to about half a line of overlap, because PyMuPDF line boxes span ascender to descender and normal leading makes adjacent boxes overlap slightly. And none of the veto rules may fire: the previous line ends in ":" (a label), either line looks like a table row or a bibliography entry, either looks like a header/footer, the next line starts a new structural block (bullet, "Figure…", "3.1 Results"), or a sentence boundary coincides with extra leading. In multi-column pages, lines must also share a column. (extract_native_blocks.py:87–150)

How are two-column pages detected and ordered?

A page is treated as two-column only on strong evidence: ≥ 16 lines, of which ≥ 12 are "narrow" (less than 60% of page width), at least 5 narrow lines on each half, and an average narrow-line width ≤ 42% of the page. Wide blocks and the header band stay column-less. The sort then emits: full-width blocks above the columns, the whole left column, the whole right column, full-width blocks between/below. Hyphenated line ends are joined without the hyphen when merging. (extract_native_blocks.py:365–452)

What block kinds exist, and why do they matter?

title, abstract, keywords, caption, table, reference, bullet, label, paragraph, and line. The kind drives three later decisions: whether the block is translated at all (reference never is), how much its box may grow to absorb translation expansion (paragraphs and abstracts get generous height, captions and table rows almost none), and typography (titles keep larger minimum sizes and tighter line-height). Classification mixes text cues ("Abstract", "Fig.", bullet markers — including tab-indented bullets, which once masqueraded as table rows) with geometry (a wide block near the page top in large type is a title; posters get a taller title band). (extract_native_blocks.py:165–352)

How does it know where the bibliography starts?

Per-line patterns ([12], "Author (2019)" + DOI/URL…) catch some entries, but citation styles vary too much for that alone. So once a standalone heading — "References", "Bibliography", "Literature cited", "Works cited" — appears in reading order, every block after it is reclassified as reference. The rule is guarded to the document's latter half, so an inline "References:" mention early in the body can't accidentally mute the rest of the document. (extract_native_blocks.py:205–254)

What about lines that never become blocks at all?

Lines with fewer than 2 letters, or more digits than letters — page numbers, y-axis values, "42%", dates — are filtered out before block creation (is_translatable_native_text). They still matter later: their rectangles are collected separately (collect_untranslatable_line_rects) so that when a neighbouring block is redacted, the redaction is trimmed away from them and they survive on the page. (extract_native_blocks.py:27–40, translate_pdf_direct.py:619–622)

Q4How does the service know what language the document is written in?

Short answer: it doesn't guess unless it has to. If the caller supplies source_lang, that value is used as-is and detection never runs. Otherwise, the PDF's own metadata language wins when it maps to an EU code; failing that, cleaned text samples from the document are sent to the translation backend, which returns an ISO 639-1 code — with en as the last-resort fallback. (translate_pdf_direct.py:515–519, translator_llm.py:203–242)

If the detected (or declared) source equals the target, the run refuses to continue rather than "translate" a document into its own language.

Supporting questions

Why are the detection samples cleaned first?

Raw PDF lines are full of things that fool language detectors: URLs, email addresses, number-dense rows, and fragments too short to carry signal. Samples must be ≥ 24 characters with ≥ 12 letters, must not contain URLs/emails, and must not be digit-heavy; survivors are concatenated into ~320-character clumps (max 10) so the model sees a few solid paragraphs of prose instead of fifty scraps. (translator_llm.py:142–173)

How does each backend actually detect?

The LLM backend asks the text model directly — "respond with ONLY the ISO 639-1 code" at temperature 0 — and validates the reply against the 24 EU codes. The DeepL backend has no detection API, so it translates the first sample's first 200 characters to English and reads the detected_source_lang DeepL reports. The adaptive backend tries DeepL's method first, LLM on error. In every case an unusable answer degrades to en. (translator_llm.py:203–242, translator_deepl.py:65–86)

What happens when source and target turn out to be the same?

It depends where it's caught. Both supplied explicitly → the API rejects it up front with a 400. Detected mid-run in the direct PDF pipeline or the native document paths → a ValueError aborts the run (surfaced by the API as a 500 "Translation pipeline failed"). The HTML engine is the deliberate exception: it logs "mixed-language safe mode" and returns the document unchanged instead of failing. And the bulk EU-matrix runner treats it as success by design: when a target matches the detected source, the original file is simply copied as that language's artifact, so every input still ends with a complete 24-language output set. (translate_pdf_direct.py:521–522, translator_llm.py:582–586, run_all_eu_translations.sh)

Can a wrong declared source silently ruin a translation?

Yes — and the README warns about exactly this for the bulk runner: set SOURCE_LANG only when the whole input set is known to share one language, because a wrong declared source mistranslates every non-matching document without any error. When in doubt, leave source_lang empty and let detection run per-document.

Q5Who does the actual translating — and what happens when DeepL fails mid-document?

Short answer: one of three interchangeable backends, chosen per request by the engine field (or the TRANSLATION_ENGINE env default): llm — the self-hosted OpenAI-compatible model (vLLM, often on RunPod); deepl — DeepL only, with errors surfaced, never hidden; and adaptive — DeepL first, falling back to the LLM on any DeepL error. All three implement the same four-method contract (detect_language, translate_single_strict, translate_strings_batch, translate_nodes), so the pipelines never know or care which one is running. (app/pipeline/translator_factory.py:9–30)

The adaptive fallback is stateful: an unsupported-language error (Maltese/Irish) falls back for that call only, but a genuine service failure — quota exhausted, rate limit, auth, connection — sets a sticky "DeepL is down" flag, and the rest of the document goes straight to the LLM instead of hammering a dead quota once per block. (translator_adaptive.py:14–56)

Supporting questions

What do the LLM prompts look like?

Two shapes. Batch: up to 50 snippets are sent as a JSON object ({"0": "text", …}) with rules — translate only natural language; preserve numbers, dates, emails, URLs, ALL-CAPS acronyms, and ZXQNT… tokens exactly; reply with JSON only. The reply is fence-unwrapped, and if JSON parsing fails, a regex salvages whatever "id": "text" pairs it can. Strict single: the retry path sends one snippet at temperature 0 — "output only the translated text, do not include the source, keep short fragments concise" — capped at 1,024 output tokens. (translator_llm.py:260–425)

Where is the LLM configured, and what are the knobs?

app/core/model_config.py resolves TEXT_MODEL_URL / _API_KEY / _NAME — with legacy fallback names (TEXT_URL, RUNPOD_VLLM_HOST, VLLM_MODEL, …) that must keep working. Generation knobs: DEFAULT_NUM_PREDICT (max tokens; values under 4,096 are forced up to 8,192), LLM_TEMPERATURE (0.1 for batches, 0.0 for strict calls), LLM_BATCH_SIZE (50), and PER_REQUEST_TIMEOUT (600 s). (translator_llm.py:176–201)

What is special about DeepL's language handling?

Two things. DeepL has no Maltese or Irish: in deepl mode those targets are a hard 400 (checked up front and at call time); in adaptive mode they fall back to the LLM per call. And DeepL requires regional variants for English and Portuguese targets — configured via DEEPL_EN_VARIANT / DEEPL_PT_VARIANT, defaulting to EN-GB / PT-PT. Keys come from DEEPL_API_KEY / DEEPL_SERVER_URL (legacy: DEEPL_AUTH_KEY / DEEPL_API_URL). (app/core/engines.py:45–81, translator_deepl.py:22–63)

Does the engine choice change anything besides the text translation?

Almost nothing — deliberately. It controls the text-translation step and language detection, and that's all. Text embedded in images is always OCR'd by the vision LLM (DeepL cannot OCR); the translate-after-OCR step then honours the selected engine. And the quality guard rails of Q7 run identically on every backend's output — DeepL is verified too. (translate_pdf_image_text.py:116–127)

Why is the DeepL import lazy?

translator_factory.get_translator imports the DeepL modules only when a DeepL-backed engine is actually requested, so the default LLM-only path never needs the deepl package (or its credentials) at call time. (translator_factory.py:13–30)

Q6What stops the translator from mangling emails, URLs, and bibliographies?

Short answer: they are never shown to the translator in the first place. Before a block is translated, protect_nontranslatable_text replaces every email address, URL, and social @handle with an opaque token — ZXQNT0QXZ, ZXQNT1QXZ, … — chosen to be meaningless in every language. The prompt orders the model to preserve such tokens exactly, and after translation they are substituted back for the originals. (app/pipeline/protected_text.py:45–77)

On top of tokenization, three whole-block skip rules keep entire categories out of the translator: blocks that contain nothing but protected content, contact-identity blocks (names attached to an email or handle), and every reference block — bibliographies are canonical citations, and translating them breaks lookups. Skipped blocks keep their source text on the page, untouched. (translate_pdf_direct.py:545–552)

Supporting questions

How does token restoration cope with model damage?

Restoration is deliberately forgiving: it matches tokens with stray spaces (ZXQNT 0 QXZ), missing suffixes (ZXQNT0), case changes, and even the older token scheme in "translated" forms like OLPROTEGIDO0 (the model once translated the token prefix itself — hence the current consonant-soup design). If a token is still unrecognizable after all that, the damage is detected: contains_protected_token finding leftover token debris in the final text forces the retry path of Q7, and a still-broken retry is rejected so the block keeps its source text — an intact original URL beats a broken translated one. (protected_text.py:67–77, 102–103; translate_pdf_direct.py:572–573)

What counts as a "contact-identity" block?

A block that contains at least one protected token and whose remaining words look like a name line rather than a sentence: 2–8 words which — after ignoring label words like "contact", "email", "author", "website" — all start with a capital letter. That pattern ("Jane Doe · jane.doe@example.eu") appears on virtually every poster and factsheet, and translating the words around the email risks garbling the name itself, so the whole block is preserved verbatim. (protected_text.py:86–100)

Why exactly are references never translated?

A citation is an identifier, not prose. Readers use it to find the cited work — in search engines, DOIs, library catalogues — and those lookups only work on the original title and venue string. A translated bibliography looks scholarly but points nowhere. This is also why the reference-section detection of Q3 errs on the side of marking too much rather than too little once the References heading is seen.

How do URLs keep their trailing punctuation?

A URL at the end of a sentence — "see https://example.eu/x." — must not swallow the period into the token, or restoration would produce a broken link. The protector peels trailing punctuation (. , ; : ! ? ) ] } " ') off the matched URL and leaves it outside the token, where the translator may treat it as normal text. (protected_text.py:49–59)

Q7How does the service catch a bad translation before it lands on the page?

Short answer: every candidate translation — from any backend — passes through should_retry_translation, a stack of cheap heuristics that asks: is it empty? identical to the source? a degenerate repetition loop? mostly leaked source text? full of English stopwords despite a non-English target? A suspicious candidate gets exactly one retry with the stricter single-snippet prompt; if the retry is still suspicious, the block is rejected and its source text is kept. The failure mode is always "original text remains", never "confident garbage" and never "text disappears". (translator_llm.py:63–102, translate_pdf_direct.py:554–598)

Supporting questions

What does a "degenerate" translation look like, and how is it caught?

Low-resource targets — notably Irish and Maltese — can send a model into a loop ("…ar bheith i bhunáid ar bheith i bhunáid…"). Three tests catch it: output longer than max(2.4 × source, source + 120 chars) — legitimate EU-language expansion tops out around 1.5×, so this only fires on pathology; a unique-word ratio below 0.4 over ≥ 16 words; or any four-word phrase repeated ≥ 3 times. (translator_llm.py:37–60)

How is "the source text leaked into the output" detected?

For sources ≥ 40 characters, a SequenceMatcher comparison: a single common run ≥ max(28 chars, 45% of the source) or an overall similarity ratio > 0.82 means the model copied rather than translated. Additionally, for English → non-English with ≥ 10 output tokens, ≥ 6 English stopwords making up ≥ 22% of tokens flags untranslated English riding along. (translator_llm.py:85–101)

Why only one retry?

Diminishing returns and honest failure. If the strict prompt at temperature 0 fails the same checks twice, a third attempt rarely differs — while every retry costs an LLM round trip per block. Rejecting keeps the source text (perfectly readable, just untranslated) and the run's stats record it: blocks_retried and blocks_rejected come back in DirectTranslationStats and are printed at the end of each run. Retries only fire for blocks longer than 16 characters — for a two-word label, the checks are too noisy to act on — except that a damaged protection token always forces the retry regardless of length. (translate_pdf_direct.py:569–598)

Do the native (txt/docx/pptx) and HTML paths get the same protection?

Yes — the identical should_retry_translation guard wraps every path: per-segment in translate_text_segments.py (used by txt/docx/pptx), per-node in the HTML engine, and per-OCR-block in image-text translation. Batch translations that fail the check are individually retried with the strict prompt and individually rejected on a second failure. (translate_text_segments.py:78–93, translator_llm.py:610–640, translate_pdf_image_text.py:56–79)

Q8Translations are longer than the original — how does the text still fit the page?

Short answer: every translated block goes through a side-effect-free placement planner (_plan_block_write) that decides where and how the text can be drawn before anything touches the page. The source rectangle is grown by kind-specific amounts (paragraphs get generous height, captions barely any), clamped so it can never spill into the block below, and optionally widened sideways into genuinely free space. The planner then searches candidate boxes × line-heights (the kind's default, 1.0, 0.94) × font sizes (shrinking ×0.92 per step, down to a 7 pt floor) until the text genuinely fits. No fit at a readable size → the block is declared unplaced and its source text is preserved. (translate_pdf_direct.py:260–449)

Writing is then done in two phases per page: all source-glyph redactions are queued and applied first, and only afterwards is all translated text inserted. Finally, link annotations captured before the rewrite are restored, and the PDF is saved compacted (garbage=3, deflate). (translate_pdf_direct.py:600–698)

Supporting questions

Why must redaction be two-phase?

Adjacent line boxes in real PDFs overlap by a few points. In a naive per-block redact-then-write loop, block N+1's redaction erases part of the text just written for block N — silently blanking output. Planning everything first, then applying all of a page's redactions in one pass, then inserting all text, makes that failure structurally impossible. The single-block helper _fit_and_write_block still exists for tests, with a docstring warning not to use it in batch. (translate_pdf_direct.py:237–246, 474–498, 607–614)

Why does the planner require spare ≥ 0 instead of "close enough"?

Because PyMuPDF's insert_textbox renders nothing at all when the text overflows even slightly — it returns a negative "spare" and draws no glyphs. A lenient threshold would therefore "place" text that then silently vanishes at write time. The planner measures each candidate on a scratch page and accepts only sizes that truly fit. (translate_pdf_direct.py:203–234, 408–417)

What keeps a redaction from erasing text that must survive?

A "preserved rects" registry per page: every skipped, rejected, or unplaced block, plus the number- and symbol-only lines from Q3 that never became blocks. Each queued redaction is trimmed away from those rectangles (with a small gap, when the overlap is significant). If trimming would collapse the redaction entirely, the original rectangle is kept — a few stray glyphs behind a translation are less harmful than erasing preserved source text, and a translation drawn over un-redacted glyphs would be unreadable. (translate_pdf_direct.py:102–128, 615–660)

How are Greek, Polish, and other non-Latin-1 targets rendered?

The PDF base-14 Helvetica fonts only cover Latin-1. resolve_font_for_text checks whether the translated text needs more (any codepoint above U+00FF, or specific symbols), and if so walks a candidate list of system Unicode fonts — Noto Sans (+ Greek, Symbols, CJK), DejaVu Sans, Liberation Sans — verifying per glyph that the font actually covers the text before embedding it. Curly quotes and a few exotic symbols are sanitized to widely-covered equivalents first. Bold/italic hints from the source font name map to the matching base font when no Unicode font is needed. (app/pipeline/fonts.py:40–125)

Why do hyperlinks need explicit restoring?

Applying redactions destroys the link annotations that overlap them. So before any rewriting, every page's links are captured (with their rectangles and targets); after all text is written, they are re-inserted — deduplicated against whatever survived, keyed by rounded rectangle + link kind + URI/page. A clickable DOI stays clickable in the translation. (translate_pdf_direct.py:52–95, 693–694)

When does a block end up "unplaced", and what does the user see?

When even the largest candidate box at line-height 0.94 and 7 pt can't hold the translation — typically a tiny label whose translation tripled in length, boxed in by neighbours on all sides. The pipeline logs a warning with the block and page, counts it in blocks_unplaced, and leaves the source text visible in place. To a reader that looks like "this one label is still in English" — which is the intended, honest behaviour, not a bug. Centered blocks are widened symmetrically so their translation stays visually centered; rotated (vertical) text keeps its exact box and only shrinks. (translate_pdf_direct.py:423–429)

Q9How are .txt, .docx, and .pptx translated — and what happens to legacy .doc/.ppt?

Short answer: natively, inside their own container — a .docx goes in and a .docx comes out, with styles, images, tables, and layout untouched. All three formats share one engine-agnostic core, translate_text_segments.py: collect text segments, detect the source language if needed, translate in batches of ≤ 40 with the Q7 retry guard, and write the results back. Legacy .doc/.ppt files are first converted to their modern equivalents by headless LibreOffice (soffice --convert-to), then take the normal lane — with a clear error if LibreOffice isn't installed. (translate_text_segments.py:32–104, convert_legacy_office.py:16–46)

Supporting questions

How does .txt keep its paragraph structure?

The bytes are decoded by trying utf-8 → utf-8-sig → cp1252 → latin-1 in order. The text is then split on blank lines into segments, and the blank lines themselves are kept as segments that pass through translation untouched — so rejoining the translated list reproduces the original spacing exactly. (translate_txt.py:8–53)

Which parts of a .docx are translated?

The main body (word/document.xml), footnotes, endnotes, comments, and every header/footer part. Within each paragraph, the text runs (w:t nodes) are joined into one string so the translator sees whole sentences, not fragments split by formatting boundaries. Everything else in the zip is copied through byte-for-byte. (translate_docx.py:10–75)

What is the "first-run write-back" trade-off?

A source paragraph may be split across several runs with different formatting — say, one bolded word mid-sentence. The translation of the joined paragraph can't be mapped back onto those run boundaries (word order changes across languages), so the whole translation is written into the first run and the rest are blanked. The paragraph reads correctly and keeps the first run's style; what is lost is mid-paragraph formatting variation. That's a deliberate trade: translation coherence over per-word styling. (translate_docx.py:60–64, translate_pptx.py:53–57)

And .pptx?

Identical surgery over ppt/slides/slide*.xml and ppt/notesSlides/: per a:p paragraph, join the a:t runs, translate, first-run write-back. Slide layouts, masters, media, and animations are untouched. Speaker notes are translated too. (translate_pptx.py:10–68)

Q10What are the HTML engine and image-text translation — and why aren't they part of the public API?

Short answer: they are the advanced/fallback capabilities, reachable only through the hidden /translate/pdf/advanced route or CLI flags. The HTML engine is the older PDF path: Poppler pdftohtml converts the page to position-preserving HTML, the text nodes are translated (or replaced from a JSON mapping), and Playwright Chromium renders the HTML back to PDF at the original page size. The image-text feature OCRs embedded figures with the vision LLM and overlays translations onto the image regions. Both trade fidelity for capabilities the direct engine doesn't have. (pdf_translate_service.py:105–197, translate_pdf_image_text.py)

Supporting questions

How does the HTML engine work, step by step?
  1. The formula-policy gate runs here too, then Chromium's presence is ensured (auto-install on first use). (playwright_support.py)
  2. The first page's size is read so the output matches the source geometry. (pdf_page_size.py)
  3. pdftohtml -c -s -noframes produces one complex-layout HTML file. (convert_pdf_to_html.py:10–54)
  4. BeautifulSoup walks every text node, preserving the exact whitespace around each one; translatable nodes are batch-translated with the Q7 guard, or — in mapping mode — replaced via exact string matching from the caller's JSON (mapping_json and target_lang are mutually exclusive). (translator_llm.py:459–658, replace_html_text.py)
  5. Playwright Chromium renders the HTML to PDF; when text changed, overflow adjustment and background-image hiding are switched on. save_html=true keeps the intermediate HTML in the output bundle for debugging. (render_html_to_pdf.py)
How does image-text translation work?

For every embedded image at least 80×50 pt, a 2× crop is rendered and sent to the vision model with a prompt that asks for figure-embedded text only — body paragraphs, headers, and page numbers are explicitly excluded — returned as JSON blocks with bounding boxes normalized to a 0–1000 grid. Up to 20 blocks per region are translated by the selected backend (with the usual retry guard), then each block's rectangle is white-filled and the translation drawn on top, shrinking the font up to six times (×0.92) to fit. (translate_pdf_image_text.py:26–172, vision_llm.py:93–141)

Why is image-text off by default?

It's destructive and approximate: the white fill permanently covers part of the original raster image, and vision-model bounding boxes are estimates — a slightly-off box paints over neighbouring artwork. For most documents the figures' text is decorative or secondary; for the public API the safe default is to leave images pristine (translate_image_text=False is hard-coded on the public route). Enable it per-run via the advanced route or --translate-image-text only when figure text is essential. (routes/translate.py:127, document_translate_service.py:155)

When would I choose the HTML engine over direct?

Rarely — direct is the production path and preserves the original PDF's internals (fonts, vector art, links). The HTML engine is the fallback for documents whose text the direct extractor handles poorly, and the only path that supports mapping mode: applying an exact find→replace dictionary instead of machine translation, useful for controlled terminology substitution. Its cost is re-rendering the whole document through a browser, which approximates rather than preserves the original typography.

Q11How do I run, test, and operate the service?

Short answer: bash run.sh starts the API on port 15000 (uvicorn, app.main:app); the same pipelines are reachable without the API through cli.py. Tests are three tiers: fast unit tests (./run_tests.sh, stdlib unittest — not pytest), a curated regression suite over real fixtures (./run_regression_tests.sh), and a long-running full matrix that translates every file in input/ into all 24 EU languages (./run_all_eu_translations.sh). Docker/compose files exist for deployment.

What are the essential CLI invocations?
# Direct engine (production path), adaptive backend python cli.py --pdf-in input/doc.pdf --workdir ./work \ --target-lang es --layout-engine direct --engine adaptive --pdf-out output/ # Office / text documents python cli.py --document-in input/doc.docx --workdir ./work \ --target-lang es --pdf-out output/ # HTML engine with a JSON replacement mapping (no translation) python cli.py --pdf-in input/doc.pdf --workdir ./work \ --mapping-json replacements.json --layout-engine html --pdf-out output/

When --pdf-out is a directory, outputs are auto-named <stem>_<target_lang><ext> (mapping mode: <stem>_mapped.pdf). --source-lang is optional; --translate-image-text and --save-html are the advanced toggles.

What are the test-suite gotchas?

Three, all documented in TESTING.md/CLAUDE.md: the scripts use unittest discover, not pytest; they hard-code .venv/bin/python (override with PYTHON_BIN); and a few tests' validation expectations depend on the engine env — always pin TRANSLATION_ENGINE=llm when running them. Single module: TRANSLATION_ENGINE=llm .venv/bin/python -m unittest tests.test_api_schema.

What does the bulk EU-matrix runner produce?

run_all_eu_translations.sh translates every supported file in input/ into all 24 languages, writing to output/eu_translations/<lang>/, with per-job logs in _logs/ and a machine-readable manifest.json recording engine, timestamps, and per-job duration. When a target equals the detected source, the original is copied as that language's artifact so every input ends with a complete 24-language set. Overrides: ENGINE=, SOURCE_LANG= (dangerous — see Q4), OVERWRITE=1, INPUT_DIR=/OUTPUT_DIR=. It runs the same CLI pipeline as production — it's an integration utility, not a unit test.

Why does "Doc Generator" still appear in a few places?

History. The project began as "Doc Generator" and was later deployed as OmniLingua (the FastAPI app title and README say so). The old name still lingers in a few internals — notably the HTML-path temp-dir prefix (doc_generator_api_) — and is harmless. The service is OmniLingua.

What system dependencies does a deployment need?

Python 3.10+; poppler-utils (pdftohtml, pdftotext, pdfinfo) for the HTML engine; Playwright Chromium (auto-installed on first HTML render, or playwright install chromium up front); Unicode fonts with broad coverage (Noto/DejaVu) for non-Latin targets in the direct engine; and LibreOffice (soffice) only if legacy .doc/.ppt support is wanted. The Dockerfile bakes these in. work/ and output/ are generated artifacts — never commit them.

Q12What can go wrong — and what does the caller actually see?

Short answer: the service fails loudly before translating and gracefully during. Everything checkable up front — auth, file type, languages, engine, content policy — is a clear 401/400 before a single model call. Once a run is underway, an individual block or segment failing means its source text is kept and counted, never dropped; only whole-run problems (LLM unreachable, LibreOffice missing, detected source equals target) surface as a 500 wrapped in "Translation pipeline failed: …".

Rule of thumb when triaging: untranslated fragments in an otherwise translated document are working-as-designed guard rails (references, contact blocks, rejected or unplaced blocks — see Q6–Q8); an untranslated document means a 4xx/5xx you can find in the logs.

Supporting questions

Full list of client-visible errors?
  1. 401 — bad/missing basic auth, on any route including /docs.
  2. 400 — unsupported extension; missing or non-EU target_lang; source_lang == target_lang (both supplied); invalid engine; deepl engine with an mt/ga target; formula-heavy PDF; on the advanced route also: non-PDF upload, mapping_json together with target_lang, or invalid mapping JSON.
  3. 500 — any pipeline exception, wrapped with its message: LLM API unreachable (the one mid-run hard stop), detected source equals target, no translatable text found in the PDF, LibreOffice missing for legacy files, DeepL service errors in deepl mode (in adaptive mode these fall back instead).

(document_translate_service.py:187–192, pdf_translate_service.py:199–204)

Which failures are deliberately not errors?

Per-block rejections and unplaced blocks (source kept, counted in stats); DeepL dying mid-run under adaptive (sticky fallback to the LLM); a same-language document in the HTML engine (returned unchanged); and a same-language target in the bulk runner (original copied as the artifact). All are visible in logs/stats, none abort the run.

Where do I see what a run actually did?

The direct pipeline returns and prints DirectTranslationStats: total blocks, translated, skipped, retried, rejected, truncated/unplaced, API calls, detected source language, and — when image-text ran — regions processed and image blocks translated/rejected. The native paths return the analogous SegmentTranslationStats. The bulk runner persists per-job timing and outcomes in its manifest.json. (translate_pdf_direct.py:31–49, 700–722)
